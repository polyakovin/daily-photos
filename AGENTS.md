# Руководство для агентов

## Подготовка окружения

- Работайте из корня этого Git-репозитория и перед изменениями проверяйте `git status --short`.
- Целевая среда разработки: Node.js `24.15.0` и npm `11.12.1`. Используйте `nvm use`, затем `npm ci`.
- Проект написан на CommonJS без этапа сборки исходников. Не добавляйте транспиляцию или новые зависимости без необходимости.
- Фотографии и пользовательские данные в `content/`, `.local/`, `outputs/` и `notes/` не являются частью исходного кода и не должны попадать в Git.

## Архитектурные границы

- `src/renderer/` — браузерный UI. Здесь нельзя обращаться к Node.js API напрямую; системные возможности проходят через preload-мост.
- `src/server/` — локальный HTTP-сервер, индекс, превью и переносимое состояние фотоархива. Сохраняйте данные выбранной папки по относительным путям.
- `src/electron/` — жизненный цикл Electron, нативные диалоги, IPC и обновления. Новый IPC-контракт меняйте одновременно в `main.js`, `preload.js` и тестах.
- `index.html` и `docs/` — публичный лендинг, отдельный от интерфейса в `src/renderer/`.
- `scripts/` — операции над изображениями, геоданными и дистрибутивами. Не запускайте конвертацию с удалением исходников на реальном фотоархиве.
- `test/` повторяет границы модулей. Сервер использует процессное состояние, поэтому полный набор тестов намеренно выполняется последовательно.

## Рабочий цикл

1. Зафиксируйте список принадлежащих задаче путей и не редактируйте чужие незакоммиченные изменения.
2. Для исправления сначала добавьте или обновите узкий тест рядом с затронутым модулем.
3. Запустите целевой тест: `node --test test/<имя>.test.js`.
4. Перед завершением любого изменения кода выполните:

   ```sh
   npm run check
   npm test
   ```

5. На машине с установленными `webp`, `ffmpeg`, `exiftool` и `libheif` дополнительно выполните `npm run preflight`. Полная локальная проверка — `npm run verify`.
6. Просмотрите `git diff --check`, итоговый diff и `git status --short`. Коммитьте только пути текущей задачи.

Если внешние системные утилиты недоступны, быстрые проверки из шага 4 всё равно обязательны, а пропущенный `preflight` нужно явно указать в отчёте.

## Правила изменений

- Сохраняйте существующий стиль: два пробела, точки с запятой, одинарные кавычки и встроенный `node:test`.
- Предпочитайте небольшие чистые функции и экспортируйте их для тестирования вместо проверки поведения через приватные детали UI.
- Для файловых тестов используйте временную папку из `os.tmpdir()` и удаляйте её через `t.after()` или `finally`.
- Не выполняйте реальные сетевые запросы в тестах. Геокодирование и обновления должны проверяться через подставные зависимости.
- Не меняйте пользовательский архив, локальные индексы или настройки в ходе тестов. Для ручного запуска задавайте временные `PHOTO_DAY_CONTENT_ROOT` и `PHOTO_DAY_STATE_ROOT`.
- Не публикуйте релиз и не используйте секреты подписи без прямого запроса. `npm run dist:mac:local` предназначен только для локального неподписанного артефакта; релиз проходит через `npm run dist:mac:release`.

## Критерий готовности

- Поведение покрыто тестом, `npm run check` и `npm test` проходят.
- Для изменений конвертации или упаковки пройден `npm run preflight`; для macOS-артефакта — соответствующая `verify:mac`-проверка.
- В diff нет фотографий, локального состояния, журналов, секретов и несвязанных изменений.
- Изменения пользовательского поведения отражены в `README.md`.
